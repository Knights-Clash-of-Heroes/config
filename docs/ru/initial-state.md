# Начальное состояние

> [!WARNING]
> **Формат `initial_state.json` в этом репозитории несовместим с оригинальной игрой.**
>
> Он был разработан с нуля, когда оригинальных файлов игры ещё не было, и построен по образцу `config.json` (id ссылаются на таблицы конфигурации, размещение через `chunk_id` + `position`). Разработчики нашли оригинальные файлы игры только сейчас, почти через 5 лет после её закрытия, и оригинальный клиент **не** использует этот формат. Оригинальный клиент получает данные из ответа сервера на `initialize`, у которого другая структура, состоящая из блоков (см. [Оригинальный формат](#оригинальный-формат-найденный-в-клиенте)).
>
> Пока файл не перенесён на новый формат, считайте его **черновиком королевства нового игрока**, а не прямой заменой тому, что ожидает оригинальный клиент. Сервер, работающий с оригинальным клиентом, должен преобразовывать его в блоки `initialize`, описанные ниже.

## Текущий формат (устаревший черновик)

Именно это описывают `initial_state.json` и `initialStateSchema` в `src/schemas/initial-state.ts`. Все объекты строгие: неизвестные свойства приводят к ошибке валидации.

| Свойство                  | Тип              | Описание                                                          |
| ------------------------- | ---------------- | ----------------------------------------------------------------- |
| kingdom.resources         | Resource[]       | Начальное количество каждого ресурса (`resource_id`, `quantity`). |
| kingdom.buildings         | PlacedBuilding[] | Здания, размещённые в королевстве (`building_id` + размещение).   |
| kingdom.kingdom_chunk_ids | int[]            | Участки земли королевства. Размещение возможно только на них.     |
| kingdom.units             | PlacedUnit[]     | Юниты, размещённые в королевстве (`unit_id` + размещение).        |

Размещение задаётся через `chunk_id`, `direction` (см. [Direction](./enums/direction.md)) и `position` (см. [Position](./interfaces/position.md)). `quantity` — число или строка `"maximum"`.

```json
{
    "kingdom": {
        "resources": [{ "resource_id": 1, "quantity": 5000 }],
        "buildings": [{ "building_id": 1, "chunk_id": 5, "direction": "north", "position": { "x": 0, "y": 0 } }],
        "kingdom_chunk_ids": [1, 2, 3],
        "units": [{ "unit_id": 1, "chunk_id": 8, "direction": "north", "position": { "x": 3, "y": 4 } }]
    }
}
```

`npm run validate` по-прежнему проверяет этот формат, включая существование каждого id в `config.json`.

## Оригинальный формат (найденный в клиенте)

Оригинальный клиент никогда не читает документ «kingdom». Он получает от сервера **частичный JSON-объект, разбитый на блоки**, и вливает каждый блок в локальное состояние (`economics/GlobalResponseParser.as` в декомпилированном клиенте). Ответ на `initialize` может содержать все блоки ниже; последующие ответы содержат только изменившиеся блоки.

| Блок                      | Структура (как её читает клиент)                                              | Примечания                                                        |
| ------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `player`                  | `{ player_id, sync, level, energy, energyRestore, adInfo, ...поля ресурсов }` | `player_id` обязателен и становится id игры (`gid`).              |
| `storage`                 | `{ wood, stone, iron, population }`                                           | Хранилище ресурсов, простые числа.                                |
| `playerStats`             | произвольный объект; применяются только ключи, существующие в классе клиента  | Используются поля `day`, `dayHourReset` и др. (`PlayerStats.as`). |
| `inventory`               | `{ "<id предмета>": количество }`                                             | Количество `0` удаляет предмет.                                   |
| `recipes`                 | словарь по id                                                                 | Рецепты игрока.                                                   |
| `unlocks`                 | словарь по id                                                                 | Наличие id в словаре означает «разблокировано».                   |
| `researches`              | словарь по id                                                                 |                                                                   |
| `missions`, `pveMissions` | словарь по id                                                                 |                                                                   |
| `heroes`                  | `{ "<id героя>": { ... } }`                                                   | Каждая запись загружается в объект информации о герое.            |
| `entityModified`          | патч, применяемый к локальной базе сущностей клиента                          |                                                                   |

Блоки `deadUnits`, `interaction`, `globalRecipes`, `payments`, `paymentsLog`, `modules`, `corovan`, `itemParts`, `clan`, `boosters`, `gwmap`, `mercenaries` и `runes` тоже существуют, но в этом репозитории пока не описаны.

Блоки, которые встречаются только в ответе на `initialize`: `clientVars`, `settings`, `dailyBonus.day`, `new_player`, `maintenance`, `quests`, `obstacles`.

Основные отличия от устаревшего черновика:

- Ресурсы — **именованные поля** (`money`, `cash`, `wood`, `stone`, `iron`, `energy`, `population`), а не записи с `resource_id`.
- Коллекции — **словари по id**, а не массивы объектов.
- Город собирается из локальной карты клиента, объединённой с данными `initialize`, а не из списков `chunk_id` + `position` в ответе.
- Значение `"maximum"` не используется; сервер отправляет конкретные числа.

### Что пока неизвестно

Внутренняя схема большинства блоков и способ размещения городских сущностей (зданий, юнитов) внутри `initialize` **пока не описаны**. Они находятся в методах `loadFromObject` / `load` классов декомпилированного клиента. Начальные значения (уровень, ресурсы, население) найдены не были; значения эталонного сервера — оценочные. Не считайте числа в `initial_state.json` оригинальными.

## План миграции

1. Описать схему каждого блока по декомпилированному клиенту и добавить Zod-схему для каждого блока.
2. Заменить `initial_state.json` форматом на основе блоков (или добавить конвертер из устаревшего черновика в блоки).
3. Обновить `src/validation.ts`, чтобы проверки ссылочной целостности соответствовали новому формату.
4. Убрать предупреждение выше, когда файл будет соответствовать оригинальному формату.
